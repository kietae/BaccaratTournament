바카라 토너먼트 앱

사내 직원 이벤트용 모바일 바카라 토너먼트. QR로 접속해 닉네임만으로 참가하고, 정해진 판수 동안 실시간으로 베팅하며, 최고 배팅자가 가로 → 세로 순서로 카드를 직접 쪼는다. 최대 500명 동시 접속을 목표로 하며, 매도(빅로드)와 딜러 콜이 전 참가자에게 동기화 재생된다.

01

개요

여러 명이 각자의 휴대폰으로 접속해 동일한 바카라 판을 실시간으로 즐기는 토너먼트형 웹앱. 모든 참가자는 동일한 초기 칩으로 시작해 정해진 판수를 플레이하고, 마지막에 칩을 가장 많이 보유한 사람이 우승한다.

  • 사용 목적 — 불특정 다수 대상 상용 서비스가 아닌 사내 직원 이벤트용 내부 도구. 최대 500명 동시 접속 지원이 목표
  • 참가 방식 — 앱 설치 없이 모바일 브라우저로, 관리자가 띄운 QR코드를 스캔해 입장
  • 승리 조건 — 관리자가 설정한 라운드 수를 모두 마쳤을 때 보유 칩이 가장 많은 플레이어
  • 덱 — 8덱 슈 사용, 서버가 셔플·딜링을 전담
  • 차별점 1 — 매 라운드 결과가 매도(Big Road)로 실시간 시각화
  • 차별점 2 — 그 판에서 가장 많이 베팅한 사람이 자신의 폰에서 카드 모서리를 직접 드래그해 쪼아서 공개
  • 차별점 3 — 메인 베팅 외에 페어 · 뱅커6 · 플레이어7 계열 사이드 베팅 지원
  • 차별점 4 — 카드 배분마다 실제 딜러 콜(음성 + 자막)이 전 참가자에게 동기화 재생
  • 운영 — 관리자가 별도 콘솔에서 라운드 진행을 통제(베팅 마감, 딜링, 결과 확정)
02

게임 흐름

토너먼트 생성부터 최종 순위 발표까지, 한 라운드가 반복되는 구조.

베팅 → 콜 → 딜링 → 쪼기/공개 → 정산 → 매도 갱신이 한 라운드의 기본 사이클.

03

카드 규칙 (3번째 카드)

국제 표준 퐁토방코(Punto Banco) 규칙을 따른다. 3번째 카드를 받을지는 정해진 표에 따라 자동으로 결정되며, 플레이어의 선택은 없다.

0. 내추럴

플레이어 또는 뱅커가 첫 두 장 합으로 8 또는 9(내추럴)를 만들면 그 즉시 승부가 확정되고, 반대편 총합과 무관하게 양측 모두 3번째 카드를 받지 않는다.

1. 플레이어 규칙

플레이어 첫 2장 합동작
0 ~ 53번째 카드를 받는다
6 ~ 7스탠드(받지 않는다)
8 ~ 9내추럴 — 게임 즉시 종료

2. 뱅커 규칙

플레이어가 내추럴이 아닐 때만 적용된다.

  • 플레이어가 스탠드(6·7)했다면 — 뱅커는 자신의 합이 0~5면 받고, 6~7이면 스탠드
  • 플레이어가 3번째 카드를 받았다면 — 아래 표대로 뱅커 합계와 플레이어의 3번째 카드 값을 함께 본다
뱅커 첫 2장 합3번째 카드를 받는 조건
0 · 1 · 2항상 받는다
3플레이어의 3번째 카드가 8이 아니면 받는다
4플레이어의 3번째 카드가 2~7이면 받는다
5플레이어의 3번째 카드가 4~7이면 받는다
6플레이어의 3번째 카드가 6~7이면 받는다
7항상 스탠드

카드 값 환산 — A는 1, 2~9는 숫자 그대로, 10·J·Q·K는 0으로 계산한다(예: K+7 = 7).

3. 테이블 위 배치

실제 바카라 테이블 관례를 따라, 처음 받는 2장은 세로(정방향)로 나란히 놓고, 3번째 카드는 그 아래에 가로(90˚ 회전)로 배치한다. 카드 쪼기 화면과 UI 목업의 카드 배치에 동일하게 적용.

04

역할별 기능

관리자, 플레이어, 게임 엔진, 그리고 쪼기 인터랙션 네 축으로 기능을 정리했다.

관리자 Admin

  • 토너먼트 생성(초기 칩, 라운드 수, 베팅 제한시간)
  • QR코드 생성 및 대형 화면 표시
  • 참가자 목록 확인 · 강퇴
  • 라운드 진행 제어(베팅 마감 · 딜링 시작 · 결과 확정)
  • 실시간 순위/현황 대시보드
  • 토너먼트 종료 및 최종 결과 발표

플레이어 Player

  • QR 스캔 → 닉네임만으로 즉시 참가
  • 대기실에서 참가자 확인 후 시작 대기
  • 보유 칩 상시 확인(칩 스택 시각화)
  • 메인 베팅(P/B/T) + 사이드 베팅 동시 선택
  • 매도(Big Road) 실시간 열람
  • 최고 배팅자일 때 드래그 쪼기 컨트롤 활성화
  • 최종 순위 확인

게임 엔진 Engine

  • 표준 바카라 규칙(8덱 슈, 3번째 카드 규칙)
  • 서버 단일 소스로 셔플 · 딜링 관리(치팅 방지)
  • 라운드별 결과 기록 → 매도 데이터 생성
  • 메인 + 6종 사이드 베팅 배당 계산 및 정산
  • 최고 배팅자 판별(동률 규칙 포함)
  • 딜링 단계마다 콜링 이벤트 발행

카드 쪼기 Squeeze

  • 가로로 슬쩍 본 뒤 세로로 마저 쪼는 2단계 순서 드래그
  • 덮여 있는 뒷면이 걷히며 숫자·무늬가 있는 앞면이 점점 드러나는 연출
  • 최고 배팅자 화면에서만 조작 가능
  • 다른 참가자는 진행 상황을 실시간 관전
  • 완전 오픈 전까지 카드 값은 서버만 보유
05

카드 쪼기(스퀴즈) 인터랙션 설계

실제 카지노에서 카드를 확인하는 순서 그대로 재현한다 — 먼저 가로 방향으로 옆면을 슬쩍 봐서 인덱스가 몇 개 보이는지 확인하고, 그다음 세로 방향으로 이어서 마저 쪼아 전체를 확인한다. 두 단계는 반드시 이 순서로만 진행되며, 열리는 대상은 카드 뒷면이 아니라 숫자·무늬가 있는 앞면이다 — 뒷면은 그대로 덮여 있고, 그 아래 있던 앞면이 점점 넓게 드러나는 구조다. 이 판에서 가장 많이 베팅한 플레이어에게만 조작 권한이 주어진다.

  • ① 가로 (0~35%) — 카드 왼쪽 긴 변을 기준으로 옆으로 슬쩍 밀면 흰색 앞면이 얇은 세로 띠로 드러난다. 인덱스(숫자·무늬)가 몇 개 보이는지만 확인하는 단계.
  • ② 세로 (35~100%) — ①이 끝나야만 활성화. 위아래로 이어서 드래그하면 앞면이 마저 넓게 드러나 전체를 확인.
  • 뒷면은 그대로 — 어두운 골드 패턴의 뒷면은 항상 카드 위에 남아 있고, 그 아래 있던 흰색 앞면이 점점 넓게 노출되는 방식이다.

두 단계 모두 진행률은 0~100% 스칼라 값으로 서버와 다른 참가자에게 전송된다.

STEP 1

권한 배정

베팅 마감 직후 서버가 최고 배팅자를 계산, 해당 클라이언트에만 쪼기 UI 활성화

STEP 2

① 가로로 슬쩍

좌우 드래그만 인식. 진행률 0~35%까지, 앞면이 가느다란 세로 띠로 드러남

STEP 3

② 세로로 마저 쪼기

가로 단계 완료 후 상하 드래그로 전환, 진행률 35~100%까지 이어서 오픈

STEP 4

완전 공개 · 브로드캐스트

진행률만 실시간 전송해 관전자도 같은 속도로 함께 지켜봄, 100% 도달 시 결과 확정

  • 구현 방식 — 카드 전체가 하나의 드래그 영역. 손을 떼지 않고 이어가는 단일 연속 드래그 안에서 진행률이 35%에 도달하는 순간, 내부적으로 기준축이 가로(dx)에서 세로(dy)로 이음매 없이 전환된다. 앞면(front)은 항상 하단에 고정돼 있고, 뒷면(back)에만 clip-path: inset()을 적용해 진행률만큼 걷어낸다 — 뒷면이 사라지는 만큼 앞면이 드러나는 구조.
  • 말리는 연출 — 뒷면 레이어에 perspective + rotateY/rotateX를 더하고, 걷히는 경계선을 따라 그림자 그라디언트가 함께 이동하도록 해 실제로 카드 모서리가 들려 말리는 듯한 입체감을 준다.
  • 동기화 — 실제 카드 값이 아니라 "노출 진행률(0~100%)"만 WebSocket으로 브로드캐스트, 100%에 도달하는 순간에만 서버가 카드 값을 전체 공개
  • 순서 보장 — 35%(①의 끝) 이전에는 세로 이동이 진행률에 반영되지 않는다. 손을 떼면 그 자리에 멈추고, 다시 잡으면 멈춘 진행률부터 이어간다(현재 진행률이 35% 미만이면 가로축부터, 이상이면 세로축부터).
  • 레이아웃 — 03장에서 정한 대로 처음 2장은 세로로 나란히, 3번째 카드는 그 아래 가로로 배치. 쪼기는 각 카드에 동일한 ①→② 순서로 적용. 폰을 세로로 세운 상태에서는 ②단계가 위→아래 드래그로 자연스럽게 이어진다.
  • 동률 처리 — 최고 베팅액이 같은 참가자가 여럿이면, 그 라운드에서 베팅을 먼저 확정한 사람이 쪼기 권한을 가짐
  • 미조작 시 — 제한시간 내 드래그를 시작하지 않으면 자동 공개로 전환
06

딜러 콜링

실제 바카라 딜러가 카드를 배분하며 외치는 콜을 음성 + 자막으로 재현한다. 서버가 진행 이벤트를 브로드캐스트하면 모든 참가자의 화면에서 동일한 시점에 동일한 콜이 재생되어 함께 몰입할 수 있다.

시점콜 예시형태
베팅 마감"노 모어 벳"음성 + 자막
1·2번째 카드 배분"플레이어" / "뱅커"음성 + 자막, 카드가 한 장씩 나올 때마다
카드 값 공개(쪼기 완료 시)숫자 콜(예: "식스", "제로")음성 + 자막, 진행률 100% 도달과 동기화
내추럴 성립"내추럴 에이트" / "내추럴 나인"음성 + 자막
3번째 카드 규칙 발동"플레이어 카드 추가" / "뱅커 카드 추가"음성 + 자막
승부 확정"플레이어 승" / "뱅커 승" / "타이"음성 + 자막 + 결과 이펙트
사이드 베팅 적중해당 베팅명 콜(예: "뱅커 식스!")음성 + 자막 + 이펙트
  • 구현 방식 — 콜 문구를 성우 녹음 또는 TTS로 1회 생성해 정적 오디오 파일로 번들. 서버는 이벤트 타입만 브로드캐스트하고 클라이언트가 로컬 매핑으로 재생 → 오디오를 스트리밍하지 않아 지연·동기화 문제 최소화
  • 자막 우선 — 무음/진동 모드 환경을 고려해 음성과 자막을 항상 함께 노출, 음소거 옵션 제공
  • 속도 조절 — 카드 쪼기가 진행되는 동안 카드 값 콜은 100% 오픈 시점까지 대기(스포일러 방지)
07

시스템 아키텍처

Vercel 같은 서버리스 환경은 지속 WebSocket 연결에 제약이 있어, Socket.io를 포함한 단일 Node 서버를 상시 구동 인스턴스에 배포한다.

  • 동시접속 500명 대응 — Socket.io를 WebSocket-only 모드로 운용해 폴링 오버헤드를 제거. 경량 소켓 500개는 단일 Node 프로세스로 충분히 감당 가능한 수준이며, Phase 9에서 실제 부하 테스트로 검증.
  • 재접속 복구 — 최초 입장 시 발급되는 재접속 토큰을 브라우저(localStorage)에 저장. 새로고침·연결 끊김 후에도 이 토큰으로 재인증하면 칩 잔액 · 현재 베팅 · 라운드 진행 상태를 그대로 복원.

베팅 옵션 및 정산 규칙

사이드 베팅 배당은 실제 카지노·업계 자료를 조사해 반영했다. 카지노마다 편차가 있어 대표값을 채택했고, 마지막 콤보 베팅은 표준화된 참고 자료가 없어 유사 사례를 근거로 한 추정값이다(추정 표시 참조).

확인 요청아래 배당표는 조사 자료를 바탕으로 한 제안값입니다. 확정 전에 검토 후 알려주세요 — 특히 콤보 베팅(30:1)은 추정치입니다.

메인 베팅

베팅배당비고
Player1 : 1—
Banker1 : 0.955% 커미션 적용(옵션화 가능)
Tie1 : 8적중 시 Player/Banker 베팅은 환급

사이드 베팅

베팅배당승리 조건

  • 페어 — 업계 표준 11:1(카지노에 따라 12:1). 무늬까지 일치하는 "퍼펙트 페어"는 별도 확장 옵션(25:1)으로 추후 고려 가능.
  • 뱅커 6 — 조사된 범위는 2장 12~15:1, 3장 20~23:1. 계산이 단순한 정수 배당인 12:1 / 20:1을 기본값으로 채택.
  • 플레이어 7 — 조사된 범위는 2장 6~7:1, 3장 15:1(가장 일관됨). 3장 배당은 확정, 2장은 7:1을 기본값으로 채택.
  • 콤보 베팅 — "한쪽 합 8, 다른 쪽 합 6"류 조합 베팅이 25:1로 제공되는 사례를 참고해 유사 희귀도로 30:1을 추정값으로 제안. 8덱 슈 기준 정확한 확률 시뮬레이션은 Phase 3(게임 엔진 개발) 때 함께 계산해 하우스 엣지를 확인 후 확정 권장.
